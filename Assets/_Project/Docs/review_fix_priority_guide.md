# Necrocis 리뷰 기반 작업 우선순위 가이드

## 목적
이 문서는 현재 리뷰 결과를 바탕으로,
"무엇을 먼저", "어떤 방식으로", "어디까지 끝내야 다음 단계로 넘어갈지"를 정리한 실행 가이드다.

이 문서에서 말하는 최적화는 단순히 숫자를 줄이는 작업이 아니다.
반드시 아래 3가지를 동시에 만족해야 한다.

1. **새 에러를 만들지 않을 것**
2. **지금 만들고 있는 핵심 게임플레이를 해치지 않을 것**
3. **측정 가능한 개선이 있을 것**

핵심 원칙은 다음 4가지다.

1. 먼저 **프레임 드랍과 런타임 불안정성**을 만든 요소부터 정리한다.
2. 한 단계에서 **한 종류의 문제만** 푼다.
3. 폴더 정리는 **핫패스 안정화 이후**에 한다.
4. 이 문서의 범위는 **안정성, 성능, 구조 정리**까지다. 강화 요소 추가는 이번 작업 범위에서 제외한다.

---

## 최적화 수용 조건

아래 조건을 만족하지 못하면 그 작업은 "최적화 완료"로 보지 않는다.

### 1) 에러 무증가
- 새 runtime exception이 없어야 한다.
- 씬 로드 시 missing reference, missing script, null reference가 새로 생기면 안 된다.
- 기존에 없던 콘솔 error/warning이 늘어나면 원인 분석 전까지 완료 처리하지 않는다.

### 2) 게임플레이 비회손
- 플레이어 이동, 공격, 스킬, 적 추격, 적 피격, 포털 이동, 레벨업 흐름이 기존과 같은 감각으로 유지되어야 한다.
- 최적화 과정에서 공격 타이밍, 스킬 판정 범위, 적 반응 속도, 카메라 추적 감각을 임의로 바꾸지 않는다.
- "더 빨라졌지만 손맛이 달라짐"은 성공이 아니다.

### 3) 개선 근거 확보
- 적어도 하나는 남겨야 한다:
  - Profiler 수치
  - GC Alloc 감소 확인
  - 프레임 타임 비교
  - Hierarchy/오브젝트 수 감소 기록
- 개선이 측정되지 않으면 구조만 복잡해졌을 가능성을 먼저 의심한다.

### 4) 롤백 가능성 유지
- 한 Phase 안에서도 기능 단위로 커밋을 나눈다.
- 리팩터링, 리밸런싱, 폴더 이동을 한 커밋에 섞지 않는다.
- 문제가 생기면 어느 변경이 원인인지 바로 좁힐 수 있어야 한다.

## 절대 보존할 게임플레이 기준

아래 항목은 최적화 중에도 그대로 유지되어야 하는 핵심 플레이 기준이다.

### 1) 플레이어 기본 조작
- 이동 방향과 이동 반응성
- 기본 공격 입력 반응
- 스킬 1, 스킬 2 발동 타이밍
- 플레이어 사망, 피격, 무적 처리

### 2) 전투 감각
- 투사체가 발사되는 위치와 방향
- 적중 판정의 범위와 타이밍
- 스킬 사용 후 효과가 보이는 순서
- 적이 플레이어를 인지하고 추격하는 감각

### 3) 씬 흐름
- Hub 시작
- 바이옴 진입
- 바이옴에서 허브 귀환
- 씬 전환 후 플레이어/카메라/매니저 유지 상태

### 4) 핵심 시스템 상태
- 레벨업 UI 호출 타이밍
- 직업/스탯 유지
- 엘리트 경고 및 스폰 흐름
- 포털/재단/바이옴 관련 상호작용

## 작업 중단 조건

아래 중 하나라도 발생하면 즉시 다음 Phase로 넘어가지 말고 현재 변경을 재검토한다.

### 중단 조건
- 플레이 감각이 달라졌는데 원인을 설명하지 못한다.
- 최적화 후 프레임은 좋아졌지만 콘솔 에러가 생긴다.
- 구조는 복잡해졌는데 측정상 개선이 없다.
- 임시 코드, fallback, 디버그 로그가 남아 있는 상태다.
- 리밸런싱이 같이 섞여서 "무엇 때문에 체감이 달라졌는지" 분리할 수 없다.

---

## 전체 우선순위

### 1순위: 런타임 안정성 정리
- 목표: 시작 순서, 싱글톤, 씬 부트스트랩을 예측 가능하게 만든다.
- 이유: 지금은 카메라/매니저 중복과 자동 생성 로직이 섞여 있어서, 성능 작업 전에 기본 실행 안정성이 흔들린다.

### 2순위: 전투 루프 할당 제거
- 목표: 스킬/투사체/이펙트의 `Instantiate/Destroy`를 줄여 전투 중 GC 스파이크를 없앤다.
- 이유: 체감 성능에 가장 직접적이다.

### 3순위: 적 AI 확장 비용 낮추기
- 목표: 적 수가 늘어날수록 급격히 느려지는 구조를 잘라낸다.
- 이유: 지금 구조는 적 밀도가 올라가면 CPU가 먼저 무너진다.

### 4순위: 렌더링/메모리 설정 최적화
- 목표: 현재 비주얼 수준 대비 과한 URP 옵션과 텍스처 비용을 줄인다.
- 이유: CPU 핫패스를 줄인 뒤 GPU/VRAM 낭비를 줄여야 실제 체감 개선이 난다.

### 5순위: 폴더 구조 정리
- 목표: 이후 유지보수와 협업 비용을 낮춘다.
- 이유: 지금 바로 해도 좋지 않다. 코드가 계속 움직이는 동안 구조까지 같이 흔들면 작업 비용만 커진다.

## 바로 시작할 작업 순서

## Phase 1. 런타임 안정성 정리

### 이 Phase에서 해결할 문제
- 허브 씬에 카메라가 중복으로 배치되어 있고, 싱글톤 파괴 기준도 일관되지 않다.
- 매니저와 플레이어 관련 오브젝트가 "씬 배치"와 "자동 생성" 두 방식이 섞여 있다.
- 이 상태에서는 성능 이슈를 잡아도 씬 전환, 시작 순서, 오브젝트 잔존 문제가 계속 재발한다.

### 먼저 할 것
- `Hub.unity`의 `DontStarveCamera` 중복 제거
- `GameInitializer`, `SceneLoader`, `InputManager`, `GameManager`, `PlayerController`, `PlayerStats`, `ObjectPooler`의 생성 책임 정리
- "씬에 있어야 하는 것"과 "코드에서 없으면 생성하는 것"을 하나로 통일

### 손대는 파일
- `Assets/_Project/Scenes/Hub.unity`
- `Assets/_Project/Scripts/Core/GameInitializer.cs`
- `Assets/_Project/Scripts/Camera/DontStarveCamera.cs`
- `Assets/_Project/Scripts/Core/SceneLoader.cs`
- `Assets/_Project/Scripts/Input/InputManager.cs`
- `Assets/_Project/Scripts/Player/PlayerController.cs`
- `Assets/_Project/Scripts/Player/PlayerStats.cs`
- `Assets/_Project/Scripts/Player/ObjectPooler.cs`

### 작업 방식
- 먼저 "씬 고정 배치" 기준으로 갈지, "런타임 자동 생성" 기준으로 갈지 결정한다.
- 추천은 **씬 고정 배치 + 코드에서는 검증만 수행** 방식이다.
- 자동 생성은 디버그에는 편하지만, 실제 프로젝트에서는 중복 생성과 순서 꼬임을 만든다.
- 싱글톤은 `Destroy(this)`와 `Destroy(gameObject)`가 섞이지 않도록 통일한다.
- 초기화 로그는 꼭 필요한 오류만 남기고 평시 로그는 줄인다.
- 이 단계에서 플레이어/카메라 생성 규칙이 바뀌더라도, 실제 플레이 흐름은 기존과 같아야 한다.

### 세부 작업 순서
1. `Hub.unity`에서 카메라, 플레이어, `SceneLoader`, `ObjectPooler` 실배치 상태를 먼저 확정한다.
2. `DontStarveCamera`를 하나만 남기고, 나머지 중복 컴포넌트 또는 중복 오브젝트를 제거한다.
3. `GameInitializer`에서 "없으면 생성" 코드를 줄이고, "없으면 오류를 내거나 명시적으로 복구"하는 수준으로 낮춘다.
4. `InputManager`, `GameManager`, `SceneLoader`, `ObjectPooler`, `PlayerController`, `PlayerStats`의 Awake 중복 처리 방식을 통일한다.
5. `DontDestroyOnLoad` 대상과 씬 고정 오브젝트를 표로 정리해 코드와 씬이 같은 규칙을 따르게 만든다.
6. 디버그 로그를 정리하고, 정상 부팅 경로에서 불필요한 `Debug.Log`를 줄인다.

### 이 Phase에서 하지 말 것
- 풀링 구조 변경
- AI 루프 최적화
- URP 옵션 조정
- 폴더 이동

### 검증 항목
- Hub 씬 시작 시 `Main Camera` 관련 오브젝트가 하나만 활성인지 확인
- Hub → Intestine → Hub 왕복 후 `InputManager`, `SceneLoader`, `GameManager`, `ObjectPooler` 인스턴스 수 확인
- 플레이어가 씬 전환 후 중복 생성되지 않는지 확인
- 콘솔에 duplicate singleton 관련 로그가 남지 않는지 확인
- `DontDestroyOnLoad` 오브젝트가 의도한 것만 유지되는지 확인
- 플레이 시작 위치, 카메라 추적, 포털 진입, 허브 귀환이 기존과 동일한지 직접 확인

### 권장 커밋 단위
- 커밋 1: `Hub.unity`와 카메라/매니저 배치 정리
- 커밋 2: 런타임 싱글톤/초기화 코드 정리
- 커밋 3: 로그 및 검증 보조 코드 정리

### 완료 기준
- 허브 진입 시 카메라가 하나만 살아 있다.
- 플레이어/입력/씬 로더/풀러가 중복 생성되지 않는다.
- 씬 전환 후에도 인스턴스 수가 예측 가능하다.
- Play 모드 시작 직후 콘솔 로그가 핵심 오류 외에는 조용하다.
- 시작, 진입, 귀환 흐름에서 플레이 감각 변화가 없다.

## Phase 2. 전투 루프 할당 제거

### 이 Phase에서 해결할 문제
- 스킬 전투에서 투사체와 이펙트가 반복 생성/삭제된다.
- 기본 공격은 풀링이 있는데 스킬 쪽은 별도 경로로 돌아서 일관성이 깨져 있다.
- 전투가 격해질수록 GC Alloc가 튀고, 플레이어가 가장 민감하게 느끼는 순간에 프레임이 흔들린다.

### 먼저 할 것
- `PlayerClassSkillController`의 스킬 투사체를 풀링으로 전환
- 히트 이펙트, 부착 이펙트도 가능한 범위에서 풀링 또는 재사용 구조로 변경
- `FindObjectsByType<EnemyController>()` 폴백 제거 또는 캐시 기반으로 대체

### 손대는 파일
- `Assets/_Project/Scripts/Player/Skills/PlayerClassSkillController.cs`
- `Assets/_Project/Scripts/Player/Skills/SkillProjectile.cs`
- `Assets/_Project/Scripts/Player/ObjectPooler.cs`
- 필요 시 신규 파일:
  `Assets/_Project/Scripts/Player/Skills/SkillProjectilePool.cs`
  `Assets/_Project/Scripts/Core/EffectPool.cs`

### 작업 방식
- 기존 `ObjectPooler`를 억지로 확장하기보다,
  "기본 투사체 풀"과 "스킬 전용 풀"을 분리하는 편이 안전하다.
- `SkillProjectile`는 `Destroy(gameObject)`를 없애고 `SetActive(false)` 기반 반환으로 바꾼다.
- 이펙트는 수명만 다른 동일 프리팹이 많으니, 프리팹 키 기반 풀로 묶는 게 좋다.
- 적 탐색 폴백은 전역 탐색 대신 `EnemyController`의 활성 적 목록 캐시를 활용한다.
- 수치나 판정 범위를 바꾸는 방식으로 "가벼워진 것처럼 보이게" 만들지 않는다.

### 세부 작업 순서
1. 현재 스킬별로 어떤 프리팹이 생성되는지 목록화한다.
2. "투사체", "즉발 이펙트", "타겟 부착 이펙트"를 분리해서 풀링 대상 우선순위를 정한다.
3. `SkillProjectile` 수명 종료와 명중 종료를 `Destroy`가 아닌 반환 API로 바꾼다.
4. `PlayerClassSkillController`의 `CreateProjectileObject`, `SpawnSkillEffect`, `SpawnAttachedSkillEffect`를 풀 경유로 변경한다.
5. 프리팹이 없는 경우 생성하는 fallback 구체 이펙트도 반복 생성하지 않도록 별도 풀이나 단일 재사용 전략을 넣는다.
6. `FindObjectsByType<EnemyController>()` 폴백이 필요한 부분은 캐시 목록 또는 더 좁은 공간 쿼리로 대체한다.

### 주의할 점
- 풀링 전환 시 상태 초기화 누락이 가장 흔한 버그다.
- `SkillProjectile`는 이전 타겟 히트 기록, 방향, lifetime, debuff 상태를 반드시 초기화해야 한다.
- 이펙트 풀링은 "보여야 할 순간에 이미 사용 중"인 경우의 처리 정책이 먼저 정해져야 한다.
- 이 단계에서 스킬의 쿨다운, 데미지, 타격감, 이펙트 재생 순서를 바꾸지 않는다.

### 검증 항목
- Mage/Archer 스킬 1, 2를 연속 사용해도 투사체 기능이 기존과 동일한지 확인
- 적중 이펙트가 위치와 지속시간 기준으로 정상 동작하는지 확인
- 스킬이 빗나갔을 때 오브젝트가 정상 반환되는지 확인
- Unity Profiler에서 스킬 연타 구간 GC Alloc가 감소했는지 확인
- 풀 오브젝트가 비정상적으로 계속 누적되지 않는지 Hierarchy 또는 Profiler로 확인
- 스킬 사용감이 달라졌는지 직접 플레이로 체크하고, 달라졌다면 원인을 남긴다.

### 권장 커밋 단위
- 커밋 1: `SkillProjectile` 반환 구조 도입
- 커밋 2: `PlayerClassSkillController` 투사체 생성 경로 풀링 전환
- 커밋 3: 스킬 이펙트 풀링 및 폴백 제거

### 완료 기준
- 스킬 연타 중 `Instantiate/Destroy` 호출이 급감한다.
- 투사체/이펙트 생성 실패 없이 기존 기능이 유지된다.
- 대량 스킬 사용 시 GC Alloc가 눈에 띄게 줄어든다.
- 스킬 타이밍과 전투 감각이 기존과 다르지 않다.

## Phase 3. 적 AI 확장 비용 낮추기

### 이 Phase에서 해결할 문제
- 적 수가 늘수록 Separation 계산 비용이 빠르게 커진다.
- `AggroDebris`는 효과 유지 시간 동안 전체 적을 반복 검색한다.
- 일부 경로에서 `Camera.main`, 전역 검색, 매 프레임 높이 샘플링이 반복된다.

### 먼저 할 것
- `AggroDebris`의 전역 적 검색 제거
- `EnemyController`의 Separation 계산을 전체 순회에서 공간 분할 기반으로 변경
- `SyncHeight`를 "위치가 실제로 바뀔 때만" 갱신
- `Camera.main` 의존과 반복적인 전역 탐색 최소화

### 손대는 파일
- `Assets/_Project/Scripts/Enemy/AggroDebris.cs`
- `Assets/_Project/Scripts/Enemy/EnemyController.cs`
- `Assets/_Project/Scripts/Enemy/EnemySpawner.cs`
- `Assets/_Project/Scripts/Enemy/EnemyProjectile.cs`
- `Assets/_Project/Scripts/Camera/Billboard.cs`

### 작업 방식
- 가장 먼저 `AggroDebris`를 `EnemyController.ActiveEnemies` 같은 캐시 컬렉션 기반으로 바꾼다.
- 그 다음 적 분리 계산을 셀 단위로 나누는 간단한 spatial hash를 넣는다.
- 처음부터 ECS/Burst로 가지 말고, 현재 OOP 구조 안에서 비용이 큰 루프만 잘라낸다.
- 높이 갱신은 "타일 경계 이동 시" 또는 "실제 위치 변화량이 임계값 이상일 때"만 재계산한다.
- 적이 멍해지거나 덜 공격적으로 보이는 방향의 최적화는 허용하지 않는다.

### 세부 작업 순서
1. 적 활성 목록 접근을 공식 API로 노출할지, 읽기 전용 컬렉션으로 노출할지 먼저 정한다.
2. `AggroDebris`를 활성 적 캐시 기반으로 변경하고, 매 프레임 전체 탐색을 제거한다.
3. `EnemyController`의 위치를 셀 단위로 등록하는 간단한 공간 해시를 만든다.
4. Separation 계산을 "같은 셀 + 주변 셀"만 보도록 바꾼다.
5. 높이 샘플링은 마지막 타일 좌표를 기억했다가 타일이 바뀔 때만 수행하게 바꾼다.
6. `EnemyProjectile`, `Billboard`, `EnemySpawner`의 `Camera.main` 및 반복 탐색 의존을 캐시로 바꾼다.

### 주의할 점
- Separation 최적화는 이동 느낌을 바꿀 수 있으므로 "같은 동작인데 가벼워지는 방향"으로만 가야 한다.
- Spatial hash는 적 등록/해제 누락 시 유령 참조가 생기기 쉬우므로 `OnEnable`, `OnDisable`, `ReleaseToPool` 흐름을 같이 봐야 한다.
- 높이 갱신 빈도를 낮출 때 지형 경계에서 발이 뜨거나 박히는지 확인이 필요하다.
- 이 단계에서 적의 감지 범위, 이동 속도, 공격 주기 같은 밸런스 값은 건드리지 않는다.

### 검증 항목
- 적 1마리, 10마리, 30마리 이상 구간에서 프레임 타임 비교
- 엘리트 사망 후 `AggroDebris` 효과가 정상 전파되는지 확인
- 적 무리 이동 시 겹침, 떨림, 제자리 회전 이상이 없는지 확인
- 경사/단차 이동 시 적 Y 위치가 튀지 않는지 확인
- 전투 중 `Camera.main` 접근이나 전역 검색 호출 수가 줄었는지 코드/프로파일러로 확인
- 플레이어가 느끼는 적 압박감과 추격 반응이 기존과 달라지지 않았는지 직접 확인

### 권장 커밋 단위
- 커밋 1: `AggroDebris`와 적 활성 목록 정리
- 커밋 2: Separation 공간 분할 도입
- 커밋 3: 높이 갱신과 카메라 참조 캐시 정리

### 완료 기준
- 적 수가 늘어도 프레임 타임이 급격히 튀지 않는다.
- 잔해 효과, 분리 이동, 추격 로직이 기존처럼 동작한다.
- 적 수 증가 시 CPU 병목이 완만해진다.
- 적 AI가 가벼워졌지만 덜 위협적으로 변하지는 않는다.

## Phase 4. 렌더링/메모리 설정 최적화

### 이 Phase에서 해결할 문제
- 현재 렌더 설정은 2.5D 픽셀 기반 화면 대비 무거운 옵션이 일부 켜져 있다.
- 텍스처 스트리밍과 import 정책이 정리되지 않아 메모리 사용량이 커질 수 있다.
- 이 단계는 코드 최적화가 끝난 뒤 들어가야 원인 구분이 된다.

### 먼저 할 것
- PC URP에서 불필요한 `Opaque Texture`, `Depth Texture`, `SSAO`, 추가 광원 그림자 사용 여부 재검토
- 텍스처 스트리밍 활성화 검토
- `Assets/_Project/Art/Images`의 import 설정 점검

### 손대는 파일
- `Assets/Settings/PC_RPAsset.asset`
- `Assets/Settings/PC_Renderer.asset`
- `ProjectSettings/QualitySettings.asset`
- `Assets/_Project/Art/Images/*`

### 작업 방식
- 현재 게임 화면에서 실제로 안 보이는 효과는 먼저 끈다.
- 특히 픽셀풍 2.5D에서 SSAO, 추가 광원 그림자, Opaque/Depth texture는 비용 대비 효용이 낮을 가능성이 높다.
- 텍스처는 해상도, compression, mipmap, read/write 옵션부터 점검한다.
- 이 단계는 반드시 **Profiler + Frame Debugger** 기준으로 확인해야 한다.
- 화면이 가벼워지더라도 의도한 분위기, 가독성, 전투 판독성이 나빠지면 되돌린다.

### 세부 작업 순서
1. 기준 장면 하나를 정해서 변경 전 프레임 타임과 메모리 사용량을 기록한다.
2. `PC_RPAsset.asset`에서 `Opaque Texture`, `Depth Texture`, additional light shadows를 하나씩 꺼보며 비교한다.
3. `PC_Renderer.asset`의 SSAO를 끈 상태와 켠 상태를 비교한다.
4. `QualitySettings.asset`에서 texture streaming 사용 여부와 품질별 차이를 정리한다.
5. `Assets/_Project/Art/Images`에서 큰 텍스처, 읽기 가능한 텍스처, 불필요하게 압축이 약한 텍스처를 우선 정리한다.
6. 마지막으로 Mobile/PC 프리셋 차이를 실제 목표 플랫폼 기준으로 재조정한다.

### 주의할 점
- 시각 차이가 없을 것 같아도 UI/빌보드/특수 이펙트에서 depth texture 의존이 있을 수 있다.
- 텍스처 import 변경은 리포 전체에 영향이 커서, 한 번에 많이 바꾸지 말고 묶음별로 검증해야 한다.
- 이 단계는 "코드 성능 문제를 렌더 설정으로 덮는 것"이 아니라 실제로 과한 옵션을 빼는 작업이어야 한다.

### 검증 항목
- 기준 씬에서 FPS, GPU frame time, VRAM 사용량 기록
- 그림자, 이펙트, UI, 빌보드, 타일맵 렌더링 이상 여부 확인
- 텍스처 압축 변경 후 색 깨짐, 알파 깨짐, 픽셀 번짐 여부 확인
- PC와 Mobile 프리셋 적용 시 화면 품질 차이가 의도 범위인지 확인
- 적, 투사체, 포털, UI의 가독성이 이전보다 나빠지지 않았는지 직접 비교

### 권장 커밋 단위
- 커밋 1: URP/Renderer 옵션 조정
- 커밋 2: QualitySettings 조정
- 커밋 3: 텍스처 import 최적화 묶음별 반영

### 완료 기준
- 시각 차이는 크지 않은데 GPU frame time이 줄어든다.
- VRAM 사용량과 로딩 메모리 점유가 감소한다.
- 모바일/PC 품질 프리셋 차이가 실제 목적에 맞게 정리된다.
- 분위기와 판독성이 유지된다.

## Phase 5. 폴더 구조 정리

### 이 Phase에서 해결할 문제
- 실사용 리소스, 서드파티 에셋, 문서, 데모 자산이 같은 레벨에 섞여 있다.
- 폴더명 규칙과 대소문자, 띄어쓰기, 오타가 혼재한다.
- 지금 구조는 사람과 코드 둘 다 탐색 비용이 높다.

### 먼저 할 것
- 실사용 리소스와 서드파티 에셋 분리
- 오타 및 네이밍 규칙 통일
- 코드 폴더를 "도메인"과 "시스템" 기준으로 다시 배치

### 추천 목표 구조

```text
Assets/
├── _Project
│   ├── Scenes
│   ├── Scripts
│   │   ├── Gameplay
│   │   ├── Systems
│   │   ├── UI
│   │   └── Data
│   ├── Art
│   ├── Audio
│   ├── Materials
│   └── Settings
├── _ThirdParty
│   ├── EVil Wizard
│   ├── Pixel Art
│   └── TutorialInfo
```

### 작업 방식
- 한 번에 전체 이동하지 말고, 먼저 신규 구조를 만든 다음 카테고리별로 옮긴다.
- Unity 프로젝트이므로 `.meta` 유지가 핵심이다.
- 씬/프리팹 참조가 많은 폴더부터 옮기지 말고, 참조가 적은 서드파티/문서부터 정리한다.
- `.DS_Store`, 데모 씬, `_Recovery` 같은 불필요 파일은 이 단계에서 같이 청소한다.

### 세부 작업 순서
1. 최종 목표 폴더 구조를 먼저 문서로 확정한다.
2. `Docs`, `TutorialInfo`, `EVil Wizard`, `Pixel Art` 같은 참조 영향이 비교적 낮은 폴더부터 이동한다.
3. `Prefabs`, `BiomeConfigs`, `Images/enemy` 같은 네이밍 문제를 우선 정리한다.
4. 코드 폴더는 `Gameplay`, `Systems`, `UI`, `Data` 기준으로 재배치하되, 한 번에 하나의 하위 도메인만 옮긴다.
5. 씬, 프리팹, ScriptableObject 참조가 깨지지 않았는지 매 단계마다 Unity에서 확인한다.
6. 불필요 파일 삭제 규칙과 `.gitignore` 정리를 같이 반영한다.

### 권장 폴더명 규칙
- 공백과 점 표기를 최소화한다.
- 숫자 접두어 체계를 유지할지 제거할지 먼저 결정하고 중간 혼용을 금지한다.
- `Prefab`, `BiomeConfig`, `Images`, `Enemy` 같은 영어 단수/복수 규칙을 통일한다.
- 서드파티 폴더는 `_ThirdParty` 아래로만 넣는다.

### 주의할 점
- Unity에서는 파일 이동보다 `.meta` 유실이 더 치명적이다.
- 코드 이동보다 에셋 이동이 참조 위험이 더 크므로, 에셋 이동 후 바로 씬 로딩 확인이 필요하다.
- 이 단계는 "예쁘게 정리"가 아니라 "다음 작업이 빨라지는 구조"를 만드는 작업이어야 한다.

### 검증 항목
- 주요 씬이 모두 열리는지 확인
- 프리팹 missing script 또는 missing reference 여부 확인
- ScriptableObject 참조가 유지되는지 확인
- git diff가 이동 중심으로 보이는지, 불필요 변경이 섞이지 않았는지 확인

### 권장 커밋 단위
- 커밋 1: 문서/서드파티/정리 파일 이동
- 커밋 2: 네이밍 정리
- 커밋 3: 코드 폴더 구조 재배치
- 커밋 4: 불필요 파일 제거 및 `.gitignore` 정리

### 완료 기준
- 팀원이 처음 봐도 리소스 위치를 추측할 수 있다.
- 실사용 에셋과 테스트/서드파티 에셋이 분리되어 있다.
- 폴더명 규칙이 한 번 정하면 계속 유지될 수준으로 단순하다.

## 결론

지금 가장 먼저 할 일은 **안정성 정리 → 전투 루프 풀링화 → 적 AI 스케일링 개선**이다.

즉,
- 먼저 실행이 흔들리지 않게 만들고
- 그 다음 전투 중 할당을 없애고
- 그 다음 적이 많아질수록 느려지는 구조를 자른다

그 다음에야 렌더/메모리 조정과 폴더 정리가 의미를 가진다.

이 순서가 가장 적은 비용으로 가장 큰 체감 개선을 만든다.
